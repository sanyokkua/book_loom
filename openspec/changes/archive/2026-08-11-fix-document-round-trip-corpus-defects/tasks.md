## 5. Make a zero-edit write a fixed point

- [x] 5.1 Extend the pre-parse normalization from task 4.1 to self-closed **non-void** elements generally, in `XhtmlParser`, so an `<a id="…" data-type="indexterm"/>` no longer stays open, duplicates its id and pulls a following `<h1>` inside itself. One surveyed book duplicates one id four times. → `:document` · `document-round-trip/spec.md#requirement-reassemble-a-document-with-zero-edits-without-changing-its-structure`, ADR-0025, design.md D2b
- [x] 5.2 Make an empty non-void element serialize as an explicit open/close pair rather than self-closed, in the output settings `XhtmlParser` configures, so writing a book and then writing that output produces the same bytes. ## 6. Preserve the leading line break of a preformatted block

- [x] 6.1 Prepend a line feed on serialization when a `pre`/`textarea`/`listing` element's first child text begins with a **bare line feed**, in the EPUB write path — the counterpart the HTML serialization spec requires to the parse-side rule that discards it. Doing the discard without the restore deletes a line of the book on every write. Key it on the exact character: measured on the pinned parser, a block beginning with a carriage-return–line-feed pair loses nothing on parse, so a restore written as "begins with any line break" would insert a break into a document that never lost one, and a block with no first child at all must not be reached into. → `:document` · `document-round-trip/spec.md#requirement-preserve-the-leading-line-break-of-a-preformatted-block`, DD-49
- [x] 6.2 Add an EPUB fixture whose `<pre class="poem">` content begins with **two** line breaks and assert both survive a zero-edit round trip. A fixture with only one leading break passes whether or not the bug is fixed, so it would prove nothing. → `:document` · same requirement, design.md D7

## 8. Stop detection resolving Cyrillic prose as a Western European encoding

- [x] 8.1 Constrain the detection rung of `CharsetLadder` so that, among single-byte candidates that all decode without error, it prefers the one whose decoding of the *distinguishing* bytes is coherent. Concretely: take the byte positions whose decoded character differs between the candidates, decode only those positions under each candidate, and prefer the candidate under which they fall predominantly within a single Unicode script block rather than scattered across unrelated blocks. Evaluating the whole file is what fails today — 195 Cyrillic bytes are swamped by 2,000 characters of French, and every single-byte encoding decodes every byte, so "it decoded" is not evidence. Settle the exact coherence test before coding and record it in the ADR-free design note, so two implementers cannot arrive at two heuristics that disagree on the fixtures in 8.2 and 8.3. → `:document` · `document-round-trip/spec.md#requirement-resolve-character-encoding-once-on-import-and-record-it-on-the-document`, design.md D4
- [x] 8.2 Add a TXT fixture that is mostly ASCII with a small `windows-1251` Cyrillic region, asserting it resolves to `windows-1251`. A wholly-Cyrillic fixture resolves correctly today and would pass against the unfixed code. → `:document` · same requirement, design.md D7
- [x] 8.3 Add a TXT fixture of French prose in `windows-1252`, asserting it still resolves to `windows-1252`, so the new preference cannot drag a genuinely Western European file to a Cyrillic encoding. → `:document` · same requirement, design.md D4 risk
