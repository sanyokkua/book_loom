# Tasks

These rules apply to every task. The design decisions (D1–D46) are in `design.md`; the behaviour each task delivers is
in this change's `specs/` (each task's **Satisfies** line names the requirement headings, or the design decision for
work that has no requirement).

Path prefixes: `P/` = `modules/pipeline/src/main/java/ua/bookloom/pipeline/`, `PT/` =
`modules/pipeline/src/test/java/ua/bookloom/pipeline/`, `PR/` = `modules/pipeline/src/main/resources/ua/bookloom/pipeline/`,
`U/` = `modules/ui/src/main/java/ua/bookloom/ui/`, `UT/` = `modules/ui/src/test/java/ua/bookloom/ui/`,
`A/` = `modules/api/src/main/java/ua/bookloom/api/`, `L/` = `modules/llm/src/main/java/ua/bookloom/llm/`,
`C/` = `modules/app/src/main/java/ua/bookloom/app/cli/`, `S/` = `modules/persistence/src/main/java/ua/bookloom/persistence/`,
`MSG` = `modules/ui/src/main/resources/ua/bookloom/ui/i18n/messages_en.properties` (and `messages_uk.properties`). In
groups 8 and 9 a path with no prefix (`state/…`, `screen/…`, `control/…`, `dialog/…`, `i18n/…`) is under `U/`, its
tests under `UT/`, `theme.css` is `modules/ui/src/main/resources/ua/bookloom/ui/theme.css`, and "the bundles" are the
two `MSG` files. A file a task creates is marked "new". Line numbers are those of commit `8d507357`; earlier tasks
move code, so find the symbol named beside the number.

- **Size and order.** The owner keeps this as one change, so the ~10-task norm (`AGENTS.md`, "How work is planned")
  applies per group. There are 12 numbered groups; each is a mergeable unit, and group 12 is the whole gate and the
  hand run. **The groups run strictly in number order, 1 to 12, and the tasks of a group run in number order. Nothing runs in
  parallel** — the pipeline and window groups edit the same `:api` records, message bundles, wiring and pipeline
  packages, and the CI and cleanup groups edit documents the earlier groups also edit (tasks 3.7 and 10.8 both
  edit `docs/development/testing.md`; 10.8 comes after 3.7). This paragraph is the one statement of the order; `design.md` only points here. Each
  task depends only on the repository and on earlier tasks (its **Depends on** line names the ones whose result it
  uses). `## Workflow follow-up` at the end lists the work done after archive; it has no checkboxes.
- **Every task ends green.** No task ends with a failing check, a test that does not compile, a placeholder or a
  control that does nothing. A task that removes a method, field, record component, enum constant or class updates
  every reader in every module — main code, both message bundles, test code and test doubles — in the same task; its
  **Read** line says how the list was built (a `grep`), and its **Done when** runs the check of every module it
  touched. A task that adds a constant to an `:api` enum, a variant to a sealed `:api` type or a component to an
  `:api` record updates every exhaustive `switch`, every table keyed by it and every constructor call in every
  module, with the English and Ukrainian words a new constant needs, in the same task.
- **Git.** Work on `feature/finish-app-for-release--<task>`, for example `feature/finish-app-for-release--2.4`, in the
  main checkout (worktrees made by the agent tool start from `master`). Commit the task there, check it off, then
  squash-merge one commit into `feature/finish-app-for-release` and delete the task branch. A checked task is complete
  only when that merge has succeeded (`AGENTS.md`, "Git"). Never `--no-verify`, never force-push, never merge into
  `master`.
- **Tests first, inside the task.** A task writes its tests first, runs them, and records the red output in its commit
  message; then it implements, and it ends with those tests and the module check green. A test that needs a new type
  is written in the task that creates the type: the task adds the type with members that throw, sees the test fail,
  then fills the type in. A group's acceptance class is created by the first task that can turn one of its cases
  green and gains a case with each later task that delivers a part; the task that adds the last case names the whole
  class green. In group 10 the acceptance test is `actionlint` and the first pull-request run; in group 11 it is the script check
  `scripts/check-docs.py`.
- **Closing a group.** A group closes with `./gradlew clean build check spotlessCheck` (its tail pasted), the local
  Sonar scan (`./gradlew sonar -PsonarLocal`, `docs/development/quality-and-ci.md`: 0 open issues, quality gate OK)
  and a push of the feature branch (pre-push runs the gate). These three have no checkbox of their own: the group's
  last task is not checked off before they are done.
- **A task that is built only if a measurement passes** says so in its first words ("only if 2.2 passed"). When the
  deciding task records FAIL, the conditional tasks are checked off in the commit that records the result, each with
  the note "not built: <task> failed"; the deciding task names what is removed in that case.
- **Tests.**
  - Name tests `method_state_expected`. Put no `if`, `for` or `while` in a test body; use `@ParameterizedTest`.
  - Use `@TempDir` for files. Write expected values out instead of recomputing them (`.claude/rules/testing.md`).
  - Use WireMock at the HTTP seam whenever a request or reply changes, with both the Ollama-native (`/api/*`) and the
    OpenAI-compatible (`/v1/*`) dialects where both apply. No Mockito. Tests prove BookLoom's code, never what a model
    server does.
  - Persistence is proven by the contract tests over **both** adapters, with SQLite on a temp file and the schema
    applied.
  - UI tests run on JavaFX 26's headless platform. "Wired" is shown by behaviour: drive the view-model and assert the
    node changed; fire the control and assert the recording fake was called. A layout assertion compares two nodes of
    the same run, never a pixel constant taken from a macOS shot.
  - A workflow or script task has no JUnit test: its test is the named script check, `actionlint`, `shellcheck` or
    the real run its **Done when** names.
- **Book-neutral.** Tests, fixtures, prompts, examples and documents use invented names and sentences. No name or
  sentence of a tested book enters the repository; owner books and eval outputs stay under the git-ignored
  `.temporary_context/` (see its `README.md`), never in the home folder.
- **Stored shapes.** A task that changes a stored record shape updates the in-memory adapter, the contract tests and a
  JSON round-trip test; the fingerprint of `StoredShapes` changes by itself. No task of this change edits
  `db/schema.sql` or its `PRAGMA user_version` (design D9). No migration is written: the next launch sets the old
  database aside (ADR-0043), so projects, providers and settings are reset; the task's commit message says so.
- **Cadence.** Run `scripts/test-focused.sh` while coding and `scripts/test-focused.sh --full-module` before each
  commit. Before pushing any change to a screen, a dialog or a UI word, run `scripts/ci-linux-ui.sh`. Never run two
  gates at once. A run much longer than the last baseline is hung: kill it and diagnose.
- **Checks in the running app.** A task whose **Done when** names something seen in the running app records it in its
  commit note (a screenshot path or the figures). There is no separate hand check per group; the whole window is
  walked by hand once, in task 12.3.
- **Logging is part of done** (`.claude/rules/logging.md`): INFO for lifecycle; DEBUG for every working method's
  parameters and every branch taken; TRACE for book text, prompts and replies; WARN for degraded, retried or refused
  outcomes; never a credential.
- **Errors.** Every port returns `Result<T>` with a typed `AppError`; no exception crosses a module edge
  (`.claude/rules/error-envelope.md`).
- **How to implement** (the owner's rules: DRY, KISS, YAGNI, SOLID; they hold for every task and are not repeated in
  one).
  - Smallest complete change. Before writing code ask, in this order: does this need to exist; is it already in this
    code base; does the JDK, JavaFX or an installed library do it; can it be one line. Only then write the minimum
    that works. No new dependency for a few lines.
  - Be lazy about the solution, never about the change. A task finishes every caller, test, fixture, message key and
    document its change touches; `grep` the callers before editing.
  - No speculative abstraction: no new interface, wrapper, option, setting, flag or "for later" code without a caller
    in this change. Deleting beats adding. Keep the existing layers and conventions: extend or replace the class a
    task names, and never add a second class beside it for the same job.
  - One implementation for each job. DRY is about knowledge, not about lines that look alike. Code that is moved or
    merged keeps its validation and its error handling.
  - Never cut: validation at a boundary, error handling that prevents data loss, security, accessibility, anything
    the owner asked for.
  - Tests: one focused test for each non-trivial piece of new logic; no test of trivial code, of a mock, or of what
    an external program does.
  - A shortcut with a known limit gets a one-line comment: `shortcut: <limit>, <when to upgrade>`.
  - A comment says why, in one line.
  - When a task makes code dead — classes, methods, prompts, message keys, tests, eval code — the same task deletes
    it.
  - A file may not pass 400 lines (Checkstyle `FileLength`): where a task makes a file near that limit grow, the
    task names where the new code goes, and any other touched file that would pass 400 lines is split by job in the
    same task, with the new class named in the commit.
- **Evals and the local model.** Local inference is single-flight: one model call at a time, one model resident at a
  time, never two eval runs at once. Start every Gradle eval through `scripts/gradle-lock.sh` (as
  `scripts/eval-matrix.sh` and `scripts/probe.sh` do). Screen on `gemma4:e4b-mlx` first and run `gemma4:26b-mlx` once
  at the end of a feature; use the fast loop (`scripts/probe.sh`, `--quick`, the mini book) to iterate and a whole
  suite only to confirm. Tests that need a model are tagged (`promptEval`, `liveLocal`) and never run in `check`. A
  task that measures states its pass rule and what happens when the rule is missed, and records the figures — numbers
  only, no book text — in `docs/evaluation/results-finish-release.md` (new, created by task 1.7). A blind sheet is
  read as design D1 says ("Readers"): by two model reader families, in sessions the measuring task starts itself on
  the owner's word of 2026-11-15, each writing a scores file under
  `.temporary_context/eval-artifacts/panel/scores/`; the task names the sheet, the readers and the files. No gate of
  groups 1–7 waits for the owner: his own reading of 20 paragraphs is a line of the final checklist (task 12.4). When
  a result changes a default, the task updates the requirement, `design.md` and this file in the same commit.
- **Specification and document edits.** A task that makes a statement of `AGENTS.md`, `.claude/rules/**` or a `docs/`
  page wrong corrects it in the same task; group 11 folds and deletes `docs/spec_baseline/`, so no task of groups 1–9
  adds a reference to that tree.
